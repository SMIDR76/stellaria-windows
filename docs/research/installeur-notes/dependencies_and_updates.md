# Dependency installation and auto-update design for a per-user Windows installer (state as of 2026-11)

Context: Caelestia for Windows = Zebar widget pack + .NET 10 NativeAOT resident helper (logon scheduled task) + optional .NET Framework 4.x WinForms exe. Per-user, no admin, GPL-3.0, distributed via GitHub Releases. Research date: 2026-11-16. Page dates are given where the source shows them.

## 1. Installing Zebar (MSI dependency): winget vs direct MSI download, elevation, detection

### Takeaway
Zebar ships **only as a per-machine WiX MSI** (winget manifest `Scope: machine`), so installing it **always needs one UAC elevation**, whether you go through winget or msiexec. A no-admin installer cannot avoid that; it can only limit elevation to that one step. Recommended approach: detect Zebar through its stable UpgradeCode or the HKLM Uninstall key. If it is missing or too old, try `winget install --id glzr-io.zebar -e --source winget --silent --accept-package-agreements --accept-source-agreements --disable-interactivity` from the user's (non-elevated) context; winget triggers the UAC prompt only for the MSI. If winget is missing or fails, download the MSI from a pinned GitHub release URL, check its SHA-256 against a hash embedded in your own installer/manifest, and run `msiexec /i … /qn` elevated with ShellExecuteEx "runas".

### Inferences
- Because the MSI is per-machine, `--scope user` will make winget fail with NO_APPLICABLE_INSTALLER (no user-scope installer in the manifest). Do not pass `--scope user`. Pass no scope, or `--scope machine`.
- Run winget **from the non-elevated per-user installer process**, never from an elevated child or SYSTEM. winget then triggers UAC itself for the machine-scope MSI. This avoids the "run whole installer as admin" pattern and the SYSTEM-context problem. A logon scheduled task running as the user is fine. A SYSTEM task is not.
- winget pulls the newest manifest version by default. To get reproducible installs, pin `--version 3.3.1` (or the minimum tested version). Check the result with your own detection afterwards rather than trusting the exit code alone (INSTALL_CANCELLED_BY_USER, PACKAGE_ALREADY_INSTALLED, UPDATE_NOT_APPLICABLE and REBOOT_REQUIRED should not be treated as plain failures).
- Detecting an installed Zebar version (tested order): (1) `MsiEnumRelatedProducts` with the stable UpgradeCode `{570D3DD8-FDBD-5B5C-A519-2FF34BA60B33}` then `MsiGetProductInfo(…, "VersionString")`. (2) Fallback: scan `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*` (and the WOW6432Node view) for `DisplayName = "Zebar"` with Publisher "Glzr Software Pte. Ltd." and read `DisplayVersion`/`InstallLocation`. (3) Last resort: the file version of `zebar.exe` in InstallLocation. The ProductCode is per-version (it differs between releases for WiX "major upgrade" packages), so never hard-code it for detection. Use the UpgradeCode. (This is inferred from how WiX/MSI major upgrades work; the UpgradeCode/ProductCode values come from the manifest.)
- Direct-MSI fallback: the GitHub `digest` field is convenient, but it comes from the same channel as the file. Stronger: embed the expected SHA-256 for the pinned Zebar version in your own signed installer or update manifest, and compare it with the downloaded file before running it. Elevate only that step by launching `msiexec.exe /i "<path>" /qn /norestart /l*v "<log>"` with `ShellExecuteEx` verb `runas` (UAC consent prompt), then wait on the process handle and read its exit code (0 = success, 3010 = success with reboot required, 1602 = user cancel, 1618 = another install in progress — standard msiexec codes, not verified in this session). Copy the MSI to a location that the user cannot modify between the hash check and the elevated launch, or check the hash again from the elevated context, to avoid a TOCTOU swap.
- Keep Zebar's own installer separate (as winget does). Do not repackage or chain Zebar inside your installer: the per-machine MSI owns its upgrade path and its Add/Remove Programs entry.

## 2. WebView2 Evergreen runtime: presence, detection, per-user install

### Takeaway
WebView2 Evergreen is part of Windows 11 and present on "the vast majority" of Windows 10 devices, but Microsoft still says to **check and install if missing**. Detection is a `pv` REG_SZ value under the EdgeUpdate client GUID `{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` in HKLM (WOW6432Node) and HKCU. The bootstrapper `MicrosoftEdgeWebview2Setup.exe /silent /install` installs **per-user when run non-elevated**, so a no-admin installer can handle this one without UAC.

### Cited Findings
- "The Evergreen WebView2 Runtime will be included as part of the Windows 11 operating system… some devices might not have the Runtime pre-installed, so it's a good practice to check whether the Runtime is present on the client." — [MS Learn: Distribute your app and the WebView2 Runtime (updated 2026-10-02)](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- "The vast majority of Windows 10 devices have the WebView2 Runtime installed already… A small number of Windows 10 devices don't have the WebView2 Runtime installed. We recommend that you handle this edge case" — [same page](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution) (refers to a 2022-12-14 blog post on delivering WebView2 to managed Windows 10 devices)
- Detection: inspect `pv (REG_SZ)` at `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` (per-machine, 64-bit Windows; without WOW6432Node on 32-bit Windows) and `HKCU\Software\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` (per-user). "If neither regkey exists, or if only one of these regkeys exists but its value is null, an empty string, or 0.0.0.0, this means that the WebView2 Runtime isn't installed." The alternative is the `GetAvailableCoreWebView2BrowserVersionString` API — [same page](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- Per-user vs per-machine: "If you don't run the installer from an elevated process or command prompt, the Runtime will be installed as per-user. However, a per-user install is automatically replaced by a per-machine install, if a per-machine Microsoft Edge Updater is in place." — [same page](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- Online: the ~2 MB Evergreen Bootstrapper, downloaded through the "Get the Link" URL or bundled, run with `MicrosoftEdgeWebview2Setup.exe /silent /install`. Offline: the Standalone Installer `MicrosoftEdgeWebView2RuntimeInstaller{X64/X86/ARM64}.exe /silent /install` — [same page](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- Updates: the Evergreen runtime updates itself. A **continuously running app keeps using the old runtime version until it releases its WebView2 environment or restarts** (`NewBrowserVersionAvailable` event). This is relevant for a resident Zebar — [same page](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- Fixed Version runtime is >250 MB and needs icacls ACL fixes on Windows 10 from v120 — [same page](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

### Inferences
- For Caelestia: check WebView2 (both keys) **before** installing Zebar. If it is missing, run the bundled or downloaded bootstrapper non-elevated (per-user, no UAC). Since Zebar's MSI does not declare WebView2, the theme installer must cover this gap.
- Restarting Zebar periodically (the helper already restarts it after sleep and display changes) has a side benefit: it picks up WebView2 security updates.

### Gaps
- No 2026 statistic on the share of Windows 10 machines without WebView2. Windows 10 consumer support ended 2025-10-14 (background knowledge, not fetched). ESU machines still get Edge/WebView2 updates, but this was not verified here.
- I did not verify whether the Zebar MSI's WiX bundle runs a WebView2 bootstrapper itself (Tauri's WiX template can embed `downloadBootstrapper`). Check `tauri.conf.json` `bundle.windows.webviewInstallMode`.

## 3. .NET Framework 4.8 presence; NativeAOT and the VC++ redistributable

### Takeaway
.NET Framework 4.8 is built into Windows 10 1903 and later, and 4.8.1 into Windows 11 22H2 and later (including 24H2 and 25H2), so a 4.x WinForms exe targeting ≤4.8 needs no installer step on any supported Windows 10/11. NativeAOT exes need no .NET runtime. The release NativeAOT link forces **dynamic UCRT** (part of Windows 10+). No source found says a VC++ redistributable is needed. Verify by running the helper on a clean VM.

## 4. Auto-update designs: polling, manifests, signatures, frameworks, rollout, UX

### Takeaway
For a small GPL project on GitHub Releases, the best fit is a **signed static JSON manifest** published as a release asset (or on GitHub Pages), fetched with a conditional request a few times a day at most. It contains version, per-file URL, SHA-256, minimum helper version, and an **ed25519/minisign signature**, modelled on Tauri's updater, which makes signatures mandatory. Use `https://github.com/<owner>/<repo>/releases/latest/download/<file>` or a conditional request to stay well under the 60 requests/hour per-IP unauthenticated API limit. Velopack is the mature off-the-shelf per-user framework (LocalAppData, `current` folder swap, deltas). winget as the updater only works well for machine-scope packages and needs an approved manifest in winget-pkgs.

### Cited Findings
**GitHub API limits**
- "The primary rate limit for unauthenticated requests is 60 requests per hour", "associated with the originating IP address". Headers: `x-ratelimit-limit/remaining/used/reset/resource` — [GitHub Docs: Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- "Making a conditional request does not count against your primary rate limit if a 304 response is returned **and the request was made while correctly authorized with an Authorization header**." Use `etag`/`last-modified` with `If-None-Match`/`If-Modified-Since`. "Poll only as often as you need to." Respect `x-poll-interval` — [GitHub Docs: Best practices for the REST API](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- GitHub release assets carry a server-computed `digest` (`sha256:…`) in the API response — [GitHub API example (Zebar)](https://api.github.com/repos/glzr-io/zebar/releases/latest)

**Tauri updater (signature model to copy)**
- "Tauri's updater needs a signature to verify that the update is from a trusted source. This cannot be disabled." The public key is embedded in the app config. The private key is supplied at build time via `TAURI_SIGNING_PRIVATE_KEY`. The static JSON has `version` (SemVer), optional `notes` and `pub_date` (RFC 3339), and `platforms.{os-arch}.{url, signature}`, where the signature is the *contents* of the `.sig` file. Tauri validates the whole file before reading the version. A dynamic server returns **204 No Content** when there is no update. Windows `installMode`: `passive` (default, progress bar, no interaction), `basicUi`, `quiet` ("only works for user-wide installs or when the app already has admin rights", "Generally not recommended"). The app "is automatically exited when the install step is executed" on Windows — [Tauri v2 Updater plugin](https://v2.tauri.app/plugin/updater/)

**Velopack (successor of Squirrel.Windows)**
- Installs to `%LocalAppData%\{packId}` with `Update.exe` and a `current` folder. "Only the `current` folder is replaced" during updates. `ApplyUpdatesAndRestart`/`ApplyUpdatesAndExit` exit the app, apply, and optionally restart. `WaitExitThenApplyUpdates` waits 60 s and then kills the app. Auto-apply on startup is on by default. Delta packages are tried first, with a fallback to the full package if there are more than `MaximumDeltasBeforeFallback` (10) deltas or the deltas are larger than the full package. Windows-only fast hooks (install/uninstall 30 s, update 15 s timeouts). A `.velopack_lock` file serialises operations. Channels and `AllowVersionDowngrade` exist — [Velopack docs: Integrating overview](https://docs.velopack.io/integrating/overview)
- The Velopack overview page does not describe automatic rollback — [Velopack docs](https://docs.velopack.io/integrating/overview)

### Inferences
- **Manifest shape** (proposal): `{ "version": "1.4.0", "pub_date": "...", "min_installer": "1.0.0", "notes_url": "...", "rollout": 100, "files": [{ "name": "caelestia-setup-1.4.0.exe", "url": "https://github.com/.../releases/download/v1.4.0/...", "sha256": "...", "size": ... }], "deps": { "zebar": { "min": "3.3.1", "tested": "3.3.1", "sha256_x64": "1d5584…" } } }` plus a detached `manifest.json.minisig` (minisign/ed25519). The helper embeds the public key, checks the signature first, then the version (anti-downgrade: reject versions ≤ installed unless the user explicitly asks for one), then the file SHA-256.
- **Authenticode** improves SmartScreen reputation and works as a second check (`WinVerifyTrust` against the expected publisher), but it costs money and needs key management. Signing the manifest with ed25519 is free and independent of Windows CA trust, and is enough for integrity. Authenticode is optional (see the code-signing research thread if one exists).
- **Polling**: the helper is resident, so check at startup (after a 5–10 min delay) and then every 12–24 h with jitter. Use the unauthenticated `releases/latest/download/manifest.json` URL (a redirect to a CDN asset, not the REST API) so you never hit the 60/h API limit. Unauthenticated 304s may still count against the API limit, since the doc requires an Authorization header for the exemption.
- **Staged rollout without telemetry**: put a `rollout` percentage in the manifest and compare it with a locally generated random bucket (0–99) stored in settings. No server-side state is needed and no ID is sent anywhere.
- **UX**: for a desktop theme, notify, don't auto-install (a tray toast or a small panel entry: "Caelestia 1.4.0 available – Update / Later / Skip this version"), with an opt-in "install updates automatically" setting. Never prompt UAC silently. A Zebar upgrade (UAC) should be its own explicit user action.
- **Privacy**: the only network traffic is GET of a static file from github.com/objects.githubusercontent.com. Send a generic User-Agent without a machine ID. Document this in the README.
- **winget as updater**: publishing `Caelestia.Windows` to winget-pkgs gives `winget upgrade` support for free, but winget-pkgs validation takes time, and a per-user custom EXE installer must declare `Scope: user` and silent switches. Treat it as an extra channel, not the primary updater.
- **Velopack vs own updater**: Velopack fits the per-user model (LocalAppData, no admin, `current` swap, deltas) and handles the "exit, swap, restart" cycle. But it owns the install layout and the uninstaller, and it expects the app to call `VelopackApp.Build().Run()` at startup, which is possible in a NativeAOT helper if the Velopack C# library is AOT-compatible (not verified). A custom updater (download signed installer → run it with `/VERYSILENT` → installer stops the helper, swaps files, restarts it) is simpler if the installer framework (e.g. Inno Setup) already exists.

## 5. Replacing files of running processes safely

### Takeaway
Don't rely on reboot-time replacement: `MOVEFILE_DELAY_UNTIL_REBOOT` **requires admin/LocalSystem** and writes to HKLM, so a no-admin installer can't use it. The robust per-user pattern: (1) signal the resident helper to exit cleanly (named event or pipe), wait, and as a last resort terminate it (with Restart Manager to find stragglers that hold files); (2) install into a **new versioned folder** and switch a pointer (the scheduled-task action path or a `current` junction), keeping the previous folder for rollback; (3) restart the helper. Velopack's `current`-folder replacement and Tauri's "exit before install" follow the same principle.

### Cited Findings
- MOVEFILE_DELAY_UNTIL_REBOOT "can be used only if the process is in the context of a user who belongs to the administrators group or the LocalSystem account". Pending operations are stored in `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\PendingFileRenameOperations`. The return value only reflects whether the registry entry was written. Directories are deleted at boot only if empty. `MOVEFILE_REPLACE_EXISTING` replaces a file's contents "provided that security requirements regarding access control lists (ACLs) are met". To rename or delete you need delete permission on the file or delete-child permission on the parent — [MS Learn: MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)
- Restart Manager stops applications in order GUI → console → services → Explorer, and restarts registered apps in reverse order. "Restart Manager shuts down application or services only if the caller has permission to do so. Note that shutdown across sessions is not supported." Windows Installer 4.0+ uses it automatically. Apps should be ready to save state when shut down — [MS Learn: About Restart Manager](https://learn.microsoft.com/en-us/windows/win32/rstmgr/about-restart-manager)
- Velopack: "only the `current` folder is replaced" on update. With multiple running instances, auto-apply "could result in the update failing or those other processes being terminated". `WaitExitThenApplyUpdates` kills the app after 60 s — [Velopack docs](https://docs.velopack.io/integrating/overview)
- Tauri on Windows exits the app before running the installer "because of a limitation in Windows installers" — [Tauri v2 Updater](https://v2.tauri.app/plugin/updater/)
- winget returns INSTALL_PACKAGE_IN_USE (0x8A150101) when the target app is running. So **Zebar must be stopped before a Zebar upgrade** (the MSI's Restart Manager integration may also prompt) — [winget return codes](https://raw.githubusercontent.com/microsoft/winget-cli/master/doc/windows/package-manager/winget/returnCodes.md)

### Inferences
- The helper is a NativeAOT console/tray exe started by a logon scheduled task. Restart Manager closes GUI apps through `WM_QUERYENDSESSION/WM_CLOSE` and console apps through Ctrl+C-like signals. A hidden-window NativeAOT process may not respond, so implement an explicit shutdown channel (a named `EventWaitHandle` such as `Local\Caelestia.Helper.Shutdown`, or a named pipe command) and fall back to `TerminateProcess` after a timeout. Same user, same session, so no admin is needed.
- Windows lets you **rename** a running exe (the image section stays mapped) but not overwrite or delete it. A cheap fallback for in-place updates: rename `helper.exe` → `helper.exe.old`, write the new `helper.exe`, restart, and delete `.old` at next start. This is a widely used technique (background knowledge, not fetched here).
- Side-by-side layout proposal: `%LOCALAPPDATA%\Caelestia\app-1.4.0\…`, `app-1.3.2\…` (kept for one-step rollback), with the scheduled task pointing to a small stable launcher or a `current` directory junction (creating a junction does not need admin, unlike symlinks without Developer Mode — background knowledge). Switching the junction or rewriting the task action is quasi-atomic. Health check: if the new helper fails to start or to signal "ready" within N seconds, switch back and record the failed version so it is not retried.
- Zebar widget-pack files (HTML/JS/CSS in `%USERPROFILE%\.glzr\zebar\…`) are read by a running Zebar. Copy them into a temp folder, then do a directory rename/swap, then ask Zebar to reload (or restart it). That avoids half-updated widgets.

## 6. Preserving user settings across upgrades and uninstall

### Takeaway
Keep user settings **outside the versioned install folder**, ideally in `%APPDATA%\Caelestia` (roaming, survives uninstall) or one level above the app folder (survives updates, removed on uninstall). This is Velopack's explicit guidance. On uninstall, offer a "keep my settings" checkbox (default: keep), and never touch Zebar's own config unless the user asks.

### Cited Findings
- Velopack: do not store settings or logs inside `current`, because updates replace it. Store "one level up (`..\`) outside of the `current` dir" to survive updates (removed on uninstall), and store important user settings in roaming `%AppData%\{packId}` to survive uninstall. "Anything stored outside RootAppDir survives uninstall." — [Velopack docs: Preserving files & settings](https://docs.velopack.io/integrating/preserved-files)
- Velopack: during install or uninstall, "the entire `{packId}` folder is replaced or removed" — [Velopack docs: overview](https://docs.velopack.io/integrating/overview)

### Inferences
- Version the settings schema (`"schemaVersion": n`) and migrate forward on first start of a new version. Keep a `settings.json.bak-<oldversion>` before migrating, so a rollback to the previous app folder still finds a compatible file.
- Uninstaller: remove the scheduled task, app folders and Start menu entries. Ask "Remove Caelestia settings too?" (default No). Ask separately "Also uninstall Zebar?" (default No: it is a third-party app that the user may use for other configs, and it needs UAC). If Caelestia changed the user's Zebar startup config, restore the user's previous Zebar config from a backup made at install time.
