# Desktop technology for the Caelestia launcher / theme platform app (2026)

Scope: choose the stack for a per-user Windows "launcher/platform" app that must reuse the existing Caelestia HTML/CSS/JS design system, browse a catalog, install/update/uninstall signed theme packs (calling the existing .NET 10 NativeAOT helper's `--install` / `--uninstall` verbs), host a settings centre and news, handle `caelestia://` deep links, run single-instance, optionally sit in the tray and auto-update itself. One developer, C# background, GPL-3.0.

Research date: 2026-11-16. Benchmarks in this space are mostly blog-grade; where numbers are weak this is said explicitly.

## Q1. Tauri 2 (Rust + WebView2): size, memory, plugins, installer, security, learning curve, peers

### Takeaway
Tauri 2 covers every functional requirement with official, maintained plugins (updater with mandatory signatures, deep-link, single-instance with deep-link forwarding, autostart, fs, http, shell/opener, notification, store, window-state) and its NSIS bundler defaults to a per-user, no-admin install in `%LOCALAPPDATA%`. It is also the stack already used by the two closest projects in this niche (Zebar, which Caelestia already depends on, and Seelen UI). The main cost is Rust for a C# developer, which can be kept small by making the Rust layer a thin shell.

### Cited Findings
- Official plugin catalogue lists 30 plugins including Updater, Deep Linking, Single Instance, Autostart, File System, HTTP Client, Shell, Opener, Notifications, Store, Process, Window State, Logging, Upload, Persisted Scope, Dialog, Clipboard, Global Shortcut, Websocket, Localhost, OS Information, Positioner, Stronghold, SQL — [Tauri plugins](https://v2.tauri.app/plugin/)
- Updater: signatures are mandatory and cannot be disabled; key pair generated by the Tauri CLI (`signer generate`), public key embedded in `tauri.conf.json`, private key supplied via `TAURI_SIGNING_PRIVATE_KEY` at build time — [Tauri updater](https://v2.tauri.app/plugin/updater/)
- Updater feed can be a static JSON on GitHub Releases/S3 (`version`, `platforms.windows-x86_64.url` + `.signature`, optional `notes`, `pub_date`) or a dynamic server returning 204 when no update; downgrades blocked by default — [Tauri updater](https://v2.tauri.app/plugin/updater/)
- Windows updater install modes: `passive` (default, small progress window, no interaction), `basicUi`, `quiet` (only works for per-user installs or when already elevated); the app is exited automatically when the installer runs — [Tauri updater](https://v2.tauri.app/plugin/updater/)
- NSIS `installMode`: `currentUser` is the default, needs no admin and installs to `%LOCALAPPDATA%`; `perMachine` and `both` require admin — [Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/)
- WebView2 bundling options: `downloadBootstrapper` (default, +0 MB), `embedBootstrapper` (+~1.8 MB), `offlineInstaller` (+~127 MB), `fixedRuntime` (+~180 MB); on Windows 10 (April 2018+) and Windows 11 the WebView2 runtime ships with the OS and is patched by Windows — [Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/)
- Deep links on Windows are delivered as a command-line argument to a new process; schemes configured under `plugins.deep-link.desktop.schemes`; `register()` / `register_all()` allow runtime registration (works in dev on Windows); combine with `tauri-plugin-single-instance` using its `deep-link` feature, registering single-instance first, so the URL is forwarded to the running instance — [Tauri deep linking](https://v2.tauri.app/plugin/deep-linking/)
- Deep-link plugin warns that a user can spoof a deep link by passing the URL as an argument, and runtime-registered schemes are not verified; requires Rust 1.90+ — [Tauri deep linking](https://v2.tauri.app/plugin/deep-linking/)
- Security model: capabilities grant/deny permissions per window/webview label; commands can be restricted via `AppManifest::commands`; `remote.urls` can allow remote origins to call specific commands; the model does not protect against insecure Rust code, lax scopes or WebView 0-days — [Tauri capabilities](https://v2.tauri.app/security/capabilities/)
- Bundle size benchmark (single run, macOS): Tauri 8.6 MiB vs Electron 244 MiB; memory with 6 windows ~172 MB vs ~409 MB; startup difference "negligible" — [Hopp, dev.to](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4). Note: macOS/WKWebView, N=1, not Windows.
- Other 2025–2026 comparison articles report idle memory ~42 MB (Tauri) vs ~168 MB (Electron) and cold start 380 ms vs 1,420 ms, but some sources find startup differences negligible; one write-up argues that the "native webview = much lighter" premise is overstated — summarised from search results incl. [tech-insider 2026](https://tech-insider.org/tauri-vs-electron-desktop-app-framework-2026/), [Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/). Treat as indicative only.
- Seelen UI: Tauri app with Svelte/TypeScript frontend and Rust backend, AGPL-3.0, ~18.5k stars; distributed via Microsoft Store (MSIX), winget (`Seelen.SeelenUI`) and GitHub Releases (`.msix` and `.exe`, signed; the `.exe` build shows in-app update notifications); community themes and a Widget SDK, website seelen.io — [Seelen UI GitHub](https://github.com/eythaann/Seelen-UI)
- Zebar (glzr-io, same org as GlazeWM): Rust crates + pnpm TS packages, widgets run in native webviews; has an in-app marketplace where users browse/install widget packs, downloaded packs stored in `%AppData%/zebar/downloads/`; GPL-3.0, ~3.1k stars; FAQ notes some users must install the WebView2 runtime — [Zebar GitHub](https://github.com/glzr-io/zebar)

### Inferences
- Caelestia already runs its widgets inside Zebar (Tauri/WebView2), so the existing CSS/JS (Material You colours, M3 Expressive motion, animated shapes) is already proven in exactly the engine Tauri uses on Windows: rendering fidelity risk is near zero.
- Zebar's marketplace (browse, download, store packs under AppData) is a direct precedent for the launcher's catalog feature on the same stack.
- The Rust side can be kept thin (window, tray, deep-link/single-instance wiring, updater, a handful of commands); zip download, signature verification and file copying can be delegated to the existing .NET helper (already has a WebSocket API and `--install`/`--uninstall` verbs), either via its WebSocket or via the shell plugin / sidecar. This limits the Rust a C# developer must write to a few hundred lines.
- System tray in Tauri 2 is a core feature (the `tray-icon` cargo feature, documented as a "Learn" guide at https://v2.tauri.app/learn/system-tray/) rather than a plugin; this was not re-verified in this session.
- Because the Tauri updater runs the NSIS/MSI installer it produced, the launcher itself should be shipped with Tauri's NSIS bundle (currentUser); the existing Inno Setup installer can either remain for the suite (launched by the launcher) or be replaced over time. Mixing both for the same binary would fight the updater.

### Gaps
- No rigorous Windows-specific (WebView2) Tauri memory benchmark was found; the commonly cited numbers are macOS or unspecified.
- Exact registry location used by the deep-link plugin on Windows (HKCU vs HKLM) is not stated in the docs page; given currentUser installs it is expected to be HKCU\Software\Classes, but this was not confirmed.
- No source quantifying the Rust learning curve for C# developers.

## Q2. .NET host with WebView2 (WPF / WinForms / WinUI 3, or extend the helper)

### Takeaway
A .NET + WebView2 host keeps everything in C#, but NativeAOT for WebView2 is only available via a community binding (WebView2Aot), WPF is not AOT-compatible, and WinUI 3 cannot be published single-file. Deep links, single-instance, tray and update all have to be assembled by hand (with Velopack for updates). Feasible, but more glue code than Tauri for the same result, with identical WebView2 rendering.

### Cited Findings
- Microsoft recommends web messages (`postMessage` / `WebMessageReceived`) over host objects: faster, simpler; host objects require COM marshalling, are slower for chatty calls and couple web and host tightly — [WebView2 performance best practices](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
- `AddHostObjectToScript` projects an `IDispatch` object into `chrome.webview.hostObjects` (sync and async proxies); for iframes, `CoreWebView2Frame.AddHostObjectToScript` accepts an origins allowlist — [WebView2 host objects](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/hostobject)
- Each WebView2 control spins up its own browser/renderer/GPU process set; share one `CoreWebView2Environment`; multiple apps can share a browser process by using the same user data folder and options; `MemoryUsageTargetLevel.Low` and `TrySuspendAsync()` reduce footprint of inactive views; Microsoft advises not to use WebView2 for splash screens because of cold-start cost — [WebView2 performance best practices](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
- No official Microsoft statement found on WebView2 + NativeAOT for WPF/WinForms; the community package WebView2Aot provides ".NET 10+ AOT-compatible bindings independent from WinForms or WPF" — [WebView2Aot on NuGet](https://www.nuget.org/packages/webview2aot)
- WinFormsComInterop (ComWrappers for WinForms AOT) notes the WebView2 wrapper does not work for newer WebView2 as of .NET 8 — [WinFormsComInterop README](https://github.com/kant2002/WinFormsComInterop/blob/main/README.md)
- WPF NativeAOT exists only as an experimental proof-of-concept fork — [lezzi/wpfaot](https://github.com/lezzi/wpfaot)
- WinUI 3 self-contained: set `WindowsAppSDKSelfContained`, xcopy-deployable unpackaged, but `dotnet publish` cannot produce a single-file EXE for WinUI 3 (native Windows App SDK files stay separate); some APIs (e.g. push notifications) need extra MSIX packages — [Windows App SDK self-contained deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)
- Avalonia 12 ships a NativeWebView / Avalonia.Controls.WebView (WebView2 on Windows) advertised as AOT and trimming compatible, with bi-directional JS interop — [Avalonia.Controls.WebView NuGet](https://packages.nuget.org/packages/Avalonia.Controls.WebView/), [Avalonia NativeWebView docs](https://v12.docs.avaloniaui.net/controls/web/nativewebview), [Avalonia site](https://avaloniaui.net/avalonia)

### Inferences
- Simplest .NET variant: WinForms (or a raw Win32 window via WebView2Aot) hosting one WebView2, JSON messages over `postMessage`, logic in shared C# with the helper. Startup/memory of the WebView2 part equals Tauri's; the .NET runtime adds its own working set (JIT build) unless AOT works.
- "Extend the existing helper as host" is attractive (one binary, already NativeAOT) only if WebView2Aot proves stable; it is a single-maintainer community dependency on the critical path, and mixing a long-running UI into the background helper changes its lifecycle (the helper is restarted around Zebar/sleep events per recent commits).
- Single instance (named mutex + named pipe to forward argv), tray (`NotifyIcon`), HKCU protocol registration and autostart (HKCU Run key) are each small in C#, but together they are the glue Tauri gives for free.

### Gaps
- No published memory/startup numbers for a WPF/WinForms + WebView2 host vs Tauri on Windows were found.
- WebView2Aot maturity/production usage not assessed beyond its NuGet listing.

## Q3. Electron

### Takeaway
Electron would work and has the most mature ecosystem, but ships its own Chromium + Node (installer roughly 50–150 MB, installed hundreds of MB) with no benefit here, since WebView2 is already on every supported Windows and Caelestia already relies on it.

### Cited Findings
- Bundle 244 MiB vs 8.6 MiB for Tauri in a like-for-like app; ~409 MB vs ~172 MB with 6 windows — [Hopp, dev.to](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4)
- Installer size figures of 50–150 MB, and 106.1 MB in one Windows 11 test, are reported by secondary sources — [tech-insider 2026](https://tech-insider.org/tauri-vs-electron-desktop-app-framework-2026/) (secondary, rough)
- ASAR integrity became stable in Electron 39 (runtime validation of app.asar against a build-time hash) — [Electron 39 release notes](https://electronjs.org/de/blog/electron-39-0)
- electron-builder 26 integrated `@electron/fuses`; NSIS target supports per-user/per-machine — [electron-builder 26.0.0 release](https://newreleases.io/project/npm/electron-builder/release/26.0.0), [OpenReplay guide](https://blog.openreplay.com/packaging-distributing-electron-apps/)
- Current Electron line in late 2026 is reported as 44.x (Chromium 152, Node 24) by a secondary source; versions conflict between sources — [tech-insider](https://tech-insider.org/electron-44-7-0-chromium-152-node-24-2026/)

### Inferences
- Electron's one real advantage (identical Chromium everywhere, cross-platform) is irrelevant for a Windows-only product that already depends on WebView2 (Chromium-based Edge engine).
- A ~100 MB launcher download to install themes that are a few MB each contradicts the project's "lightweight helper" direction.

### Gaps
- Official current Electron version and Windows-specific memory numbers were not verified from electronjs.org in this session.

## Q4. Pure native UI (WinUI 3, WPF Fluent, Avalonia)

### Takeaway
All three can produce a polished app, but none can reuse the existing CSS/JS, so the Material You palette generation, M3 Expressive motion and animated shapes would have to be rebuilt in XAML. For a one-person team whose requirement is "look exactly like Caelestia", this is the most expensive option and guarantees visual drift.

### Cited Findings
- WPF .NET 9 Fluent theme: `ThemeMode` (Light/Dark/System/None), system accent colour brushes (`AccentColor`, Light1–3, Dark1–3); setting `ThemeMode` in code is experimental (WPF0001) — [What's new in WPF .NET 9](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net90)
- WinUI 3 unpackaged self-contained is supported but not single-file — [Windows App SDK self-contained deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)
- Avalonia 12 is released (Avalonia.Native 12.0.0 listed April 2026) and offers an embedded WebView — [Avalonia.Native NuGet](https://packages.nuget.org/packages/Avalonia.Native), [Avalonia site](https://avaloniaui.net/avalonia)

### Inferences
- WPF Fluent and WinUI 3 give a Windows 11 Fluent look, which is precisely not the Caelestia (Material 3) look; matching M3 Expressive shape morphing in XAML is custom-drawing work.
- Avalonia (Skia-rendered, fully stylable) is the only native option where reproducing Caelestia would be realistic, and it can embed a WebView for parts; but that ends up as a hybrid with two UI systems to maintain.

### Gaps
- No effort estimates found for porting a Material 3 Expressive design system to XAML.

## Q5. Deep links: per-user protocol registration and secure URI handling

### Takeaway
A `caelestia://` handler is registered with a `URL Protocol` value and a `shell\open\command` of `"<exe>" "%1"`; per-user registration under HKCU\Software\Classes needs no admin. Every deep link must be treated as hostile input: Windows may split or alter the string, and anyone can invoke it, so the app must parse strictly, never act on embedded URLs/paths, and confirm with the user before installing.

### Cited Findings
- Registration: key named after the scheme with `URL Protocol = ""`, optional `DefaultIcon`, and `shell\open\command` = `"...\app.exe" "%1"`; without `URL Protocol` the handler does not launch — [Registering an Application to a URI Scheme](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa767914(v=vs.85))
- Security warning: handlers receive data from untrusted sources; quotes/backslashes can inject extra command-line parameters; some callers percent-decode and others do not; apps "that could initiate dangerous actions based on external data must first confirm those actions with the user"; test with overly long and odd URIs — [same source](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa767914(v=vs.85))
- Microsoft recommends per-user installation and per-user registration (HKCU) since Windows 7 (App Paths example) — [Application Registration](https://learn.microsoft.com/en-us/windows/win32/shell/app-registration)
- Tauri deep-link: delivered via argv to a new process, forwarded by single-instance; spoofing via manual argument is possible, validate the expected format — [Tauri deep linking](https://v2.tauri.app/plugin/deep-linking/)

### Inferences
- Recommended URI shape: `caelestia://install/<pack-id>[@<version>]` only; the app resolves the id against its own signed catalog and downloads from its own origin. Never accept a download URL, file path or script in the link.
- Read the raw command line, reject anything not matching a strict regex, cap length, and always show a confirmation dialog with pack name, author and signature status before installing.
- HKCU registration is written by the per-user installer (Tauri NSIS does it from config) and should be removed on uninstall.

### Gaps
- Behaviour of current Chromium/Edge when launching external protocols (the "Open Caelestia?" prompt, remember-choice policies) was not researched here.

## Q6. Self-update options

### Takeaway
Tauri's updater is built in, signature-enforced and per-user friendly; Velopack is the equivalent for a .NET host (per-user under %LocalAppData%, delta updates, Rust-based, MIT). A custom updater via the helper is possible but re-implements what both give for free.

### Cited Findings
- Tauri updater: mandatory signatures, static JSON on GitHub Releases, passive install mode, downgrade protection — [Tauri updater](https://v2.tauri.app/plugin/updater/)
- Velopack: cross-platform installer + updater, SDKs for C#, C++, JS, Rust, Python; feeds are static files (GitHub Releases, cloud storage); `vpk pack` builds releases; `VelopackApp.Build().Run()` must run first in `Main`; `UpdateManager.CheckForUpdatesAsync` / `DownloadUpdatesAsync` / `ApplyUpdatesAndRestart` — [Velopack docs](https://docs.velopack.io/), [Velopack C# guide](https://docs.velopack.io/getting-started/csharp)
- Velopack installs under `%LocalAppData%\{packId}` with `current\` and `Update.exe`; delta updates tried first with fallback to full (max 10 deltas by default); Windows install/update hooks with 15–30 s timeouts — [Velopack integration overview](https://docs.velopack.io/integrating/overview)
- Velopack is MIT, written in Rust, ~2.5k stars, supports delta packages; a testimonial claims updates apply and relaunch in ~2 s with no UAC prompts (user claim, not benchmark) — [Velopack GitHub](https://github.com/velopack/velopack)

### Inferences
- Theme-pack updates are a separate concern from app self-update: packs should carry their own detached signatures (e.g. Ed25519/minisign) verified before extraction, with the public key pinned in the app; the Tauri updater keys can follow the same scheme for consistency.
- Velopack could also update the existing .NET helper, but if the launcher is Tauri, the simplest model is: launcher self-updates via Tauri updater; launcher updates the helper/suite as just another signed package.

### Gaps
- Velopack NativeAOT compatibility and code-signing integration were not confirmed from primary docs in this session.

## Q7. Memory/CPU footprint numbers (Tauri vs Electron vs WebView2 hosts)

### Takeaway
Reliable Windows numbers are scarce. Available data consistently show Tauri using roughly half (or less) of Electron's memory and ~25x smaller bundles; a Tauri app and a .NET WebView2 host share the same dominant cost (the msedgewebview2 process set), so their difference is the host process only.

### Cited Findings
- 6 windows: Tauri ~172 MB vs Electron ~409 MB; bundle 8.6 vs 244 MiB (macOS, N=1) — [Hopp, dev.to](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4)
- WebView2 uses Edge's multi-process architecture; each control launches multiple processes that add memory and startup overhead; GPU acceleration allocates extra memory; cold start is the main startup cost — [WebView2 performance best practices](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
- Microsoft's end-user FAQ attributes extra WebView2 memory/CPU mostly to how apps use it — [WebView2 end-user FAQ](https://learn.microsoft.com/microsoft-edge/webview2/concepts/end-user-faq)
- Idle WebView2 figures quoted by blogs (~80 MB; 50–300 MB) are not authoritative — [helpdeskgeek](https://helpdeskgeek.com/help-desk/what-is-microsoft-edge-webview2-runtime-and-how-to-reduce-cpu-usage/)

### Inferences
- If the launcher shared Zebar's WebView2 user data folder it could share a browser process, but that also shares cookies/caches and couples the apps; better to keep a separate UDF and simply close the launcher window (or suspend the webview with `TrySuspendAsync`/Low memory target) when idle in the tray.
- For a launcher that is opened occasionally, footprint matters mostly when resident in the tray; a tray-only mode that destroys the webview and keeps only the host process is the biggest lever, and is cheapest with a Rust host.

### Gaps
- No controlled Windows benchmark comparing Tauri, WPF/WinForms+WebView2 and Electron idle memory and cold start was found; a local measurement (Task Manager Details, sum of msedgewebview2 children + host, over 15–20 min) is recommended before committing.

## Recommendation summary (synthesis, not a single source)

1. **Tauri 2 (recommended).** Reuses the Caelestia web UI unchanged in the same WebView2 engine Zebar already uses; official plugins cover deep-link + single-instance + updater + autostart + store + notifications; tray is core; NSIS `currentUser` = per-user, no admin; signed updates enforced. Same stack as Zebar and Seelen UI. Keep Rust thin and delegate Windows/theme operations to the existing .NET helper (WebSocket or sidecar). Main risk: Rust learning curve (mitigated by small surface).
2. **.NET (WinForms or raw Win32) + WebView2 + Velopack (fallback).** All C#, same rendering, but deep-link/single-instance/tray assembled manually and NativeAOT depends on the community WebView2Aot binding; WPF not AOT, WinUI 3 not single-file.
3. **Electron: not recommended** (100+ MB for no gain on Windows-only).
4. **Native XAML (WinUI 3 / WPF Fluent / Avalonia): not recommended** for this app: it discards the existing design system; Avalonia is the only one where matching the look is plausible.
